CSR vs SSR vs SSG—and hydration

This same component is configured with three server rendering modes at the route level.

After SSR/SSG HTML hydrates, the browser owns the interactive Angular component, so seeing “browser” here is expected.

CSR: client-side rendering

The server sends an application shell; browser JavaScript builds the page. It is simple and suits private dashboards, but initial content and SEO wait for JavaScript.

SSR: server-side rendering

A server renders fresh HTML for each initial request. It suits dynamic, public content, but adds server runtime cost and request latency.

SSG: prerendering

The build creates static HTML in advance. It is fast and CDN-friendly, but changing content requires another build and it cannot contain per-user data.

Hydration is a separate step

SSR and SSG answer where and when the initial HTML is created. Hydration answers how that existing HTML becomes interactive. Angular reuses server-created DOM and attaches behavior instead of discarding and rebuilding it.

Older approach: apps often destroyed server HTML and rendered again in the browser, causing extra work and visible layout changes. Modern approach: provideClientHydration() reuses it, with event replay protecting early user actions.

Avoid browser-only globals such as window, document, and localStorage during server execution. Guard them with platform checks or run browser-dependent work after rendering.
