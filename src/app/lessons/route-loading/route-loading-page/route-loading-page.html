Eager vs lazy-loaded routes

Both links render the same counter. The visible result is the same; the important difference is when the browser receives the component's JavaScript.

Before standalone: lazy-load an NgModule

{
  path: 'reports',
  loadChildren: () =>
    import('./reports/reports.module').then(
      (module) => module.ReportsModule
    )
}

The lazy NgModule declares its components and calls RouterModule.forChild() with its feature routes. This remains supported for existing applications. Modern standalone features can instead lazy-load one component with loadComponent or a plain route array with loadChildren.

Eager: component

import {{ '{' }} EagerRouteDemo {{ '}' }} from './eager-route-demo';

{{ '{' }} path: 'eager', component: EagerRouteDemo {{ '}' }}

A normal static import lets the bundler include the component immediately. Navigation is ready without downloading that component later, but every eager feature increases startup code—even if the user never opens it.

Lazy: loadComponent

{{ '{' }}
  path: 'lazy',
  loadComponent: () =>
    import('./lazy-route-demo').then(
      (module) => module.LazyRouteDemo
    )
{{ '}' }}

Dynamic import() creates a split point. The initial bundle can be smaller, while the first visit may wait briefly for the extra chunk. Later visits normally reuse the browser's downloaded code.

loadComponent vs loadChildren

Use loadComponent to lazy-load one standalone component. Use loadChildren to lazy-load a route configuration containing a feature's parent, child, guard, and provider setup. Despite its historical name, loadChildren can load a modern Routes array; it does not require an NgModule.

Practical rule: eagerly load the small, essential landing experience. Lazy-load larger or less frequently visited feature areas. Too many tiny lazy chunks can add request and navigation overhead, so split by meaningful features rather than every component.
