Lesson 8

Services vs component state

Component state belongs to one UI instance. Service state and logic can be injected into multiple consumers.

Component state: two independent instances

Increment one blue counter. Its sibling does not change because each component constructed its own state.

Service state: two consumers, one instance

Increment either purple counter. Both update because both components inject the root-provided service instance.

Ask who owns the responsibility

Keep it in the component when…

  • Only that component needs the value.
  • The state describes temporary UI details such as expanded, selected, or draft text.
  • Destroying and recreating the component should naturally reset it.

Move it to a service when…

  • Several components need the same state or behavior.
  • Business logic should remain independent of one template.
  • You need an API client, cache, authentication state, logging, or coordination.
Concern Component state Service
Default owner One component instance The injector that provides it
Sharing Pass through inputs/outputs or lift state Inject the same provided instance
Lifetime Component creation to destruction Provider scope lifetime
Template knowledge Usually presentation-oriented Should not depend on a particular view
Typical work Drafts, toggles, local selection APIs, business rules, caches, shared state

Dependency injection in this example

  1. A root-provided Injectable registers a provider with the root injector.
  2. Each panel calls inject(SharedCounter) during component construction.
  3. Angular searches the injector hierarchy and returns the existing root instance.
  4. Both templates track the service's same read-only count signal.

A service class is not automatically a singleton merely because its name ends with “Service.” Provider placement determines how many instances exist. Lesson 9 explores that scope difference directly.

Avoid the “everything service”: moving all component state into root services creates hidden global coupling. Start local, then lift state when real sharing or non-UI responsibility requires it.
